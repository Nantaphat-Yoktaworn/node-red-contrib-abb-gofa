# EGM (Externally Guided Motion) — optional second RAPID module

Full design history: `.claude/memory/project_egm_node_red_integration_plan.md` and its linked plan file.

**Two RAPID modules, one loaded at a time.** `rapid/MainModule.mod` (default, no EGM). `rapid/MainModuleEGM.mod` — full clone plus the `EGMJOINT` command and mode state machine. Kept separate (not merged) since an EGM session blocks the task for its whole duration either way; keeping it separate means every other node depends on zero-EGM-risk code, and reverting is just reloading `MainModule.mod`.

**Switching modules requires `unloadmod` first — confirmed live.** `replace=true` only replaces same-named modules; loading the other name alongside leaves both loaded → `(87,5): Global routine name main ambiguous`. Full swap: `stop` → `unloadmod` (current) → upload new file → `loadmod` (`replace=true`) → `resetpp` → `start`.

**Mode switch**: `gofa-egm`'s `start` sends `EGMJOINT` (ack `OK:EGMJOINT`) → sets a flag `ServeClient`/`ServeForever` check after `Dispatch` returns → closes sockets, `main()` runs `RunEgmJoint` (`EGMSetupUC ... "EGM_PC" \Joint \CommTimeout:=5` → `EGMActJoint` with `egm_minmax1:=[-10.0,10.0]` hard clamp → `EGMRunJoint ... \CondTime:=60`). While in EGM mode, every other socket node fails fast with "connection refused."

**Mode exit — TRAP/`EGMStop`, the current, fixed design.** Per ABB's EGM manual, `EGMStop` is meant to be called from a TRAP to end a session gracefully (returns normally, unlike an external kill). `RunEgmJoint` does `CONNECT egmStopIntNo WITH TrapEgmStop; ISignalDO ABB_Scalable_IO_0_DO16, 1, egmStopIntNo;` before starting. `gofa-egm.js`'s `stop` (and `close` during an active session) sets that signal via RWS, then polls `PING` for confirmation. `TrapEgmStop` fires → `EGMStop egmID1, EGM_STOP_HOLD;` → `RunEgmJoint` returns normally, cleanup (`IDelete`+`EGMReset`) always runs — **the RAPID task never stops**, no `resetpp`/`start` needed. Confirmed live: zero start/stop elog events across a full cycle.

**Superseded designs, do not re-implement**: (1) original design relied on `\CommTimeout` raising a comm-timeout error on silence — confirmed FALSE, task blocked 2+ min with no recovery. (2) External RWS stop (`execution/stop`→`resetpp`→`start`) worked but skipped `RunEgmJoint`'s own `EGMReset`, **leaking one controller-side EGM instance per cycle** — RobotWare caps concurrent EGM identities at **4**; ~8 leaked cycles in 90s exhausted the pool ("Too many EGM instances"). A short `\CondTime` hypothesis was tested and disproven too (session stayed blocked 70s+ after abrupt kill). The TRAP/`EGMStop` fix is the real solution — confirmed via 12 consecutive cycles, stable timing, zero instance exhaustion.

**If RAPID is externally stopped mid-EGM-session** (FlexPendant Stop, e-stop, module-switch's own stop — NOT `gofa-egm`'s own start/stop, which no longer stops the task): **never resume with a bare "continue" start — always `resetpp` first.** A bare continue resumed mid-EGM-code (program pointer left inside the EGM block), skipping `EGMReset`, causing "You have to disconnect an EGM instance using EGMReset before you can connect another." Recovery: `stop` → `resetpp` → `start`. **If the same error persists even after a genuinely fresh `resetpp`+`start`**, the problem is a stuck controller-level `EGM_PC` UC transport resource (not RAPID-side, not resettable by any RAPID instruction, not visible anywhere in RWS) — only a full controller restart clears it. After restart: Manual/Reduced mode, motors in `guardstop`, needs physical switch to Auto + motors on.

**`gofa-egm` (Node.js)**: `nodes/gofa-egm.js`. Hand-rolled proto2 codec (`decodeEgmRobot`/`encodeEgmSensor`, no protobufjs dep) — package has **zero runtime dependencies** as of 2.2.3 (the `ws` package was also replaced by a hand-rolled WS client, `nodes/lib/ws.js`, on Node's own `http`/`https`/`crypto`). Codec verified byte-for-byte against the proven `gofa-egm-python` project's `egm_pb2`. Uses `dgram`. **Action** dropdown (`start`/`stop`), overridable by `msg.payload`/`msg.payload.action`. On `start`: sends `EGMJOINT` (`ERR:EGMJOINT` → wrong module loaded, surfaced specifically); binds UDP, waits up to 2s for first frame (timeout → check `EGM_PC` config/firewall). Holds current pose until `gofa-egm-move` sets a target — never moves on connect. Output throttled (default 100ms; real frames arrive ~24ms). On `stop`/`close`-while-active: sets `ABB_Scalable_IO_0_DO16` via RWS, polls `PING` up to 8s.

**Session state lives on the shared `gofa-robot` config node** (`robot._egmActive`/`_egmTarget`/`_egmBaseline`/`_egmSocket`), same pattern as `_seqStop`/`_seqRunning`. `gofa-egm` owns the UDP socket/receive loop; **`gofa-egm-move`** (separate node) is the only writer of `_egmTarget` — takes `[j1..j6]` (or `{joints:[...]}`), checks `_egmActive`: session running → updates target, output 1; not running → unchanged message, output 2 (wire into `gofa-movej` for automatic fallback — payload shapes are directly compatible).

**Confirmed live end-to-end (GoFa 12/OmniCore C30, RobotWare 7.21.0+229)**: start → baseline hold → +3° target on joint 6 → real convergence → back to baseline → stop → PING confirms TCP restored. TRAP/EGMStop fix: 12 consecutive cycles, ~80ms start / ~1.05s stop, zero drift, zero instance exhaustion, zero stop/start elog events. Node-split (`gofa-egm`/`gofa-egm-move`/`gofa-movej`) confirmed live including the non-EGM fallback path producing real `MOVEJ` motion.

**Bug fixed (2026-07-09): UDP socket wasn't actually shared, only the flags were.** Two-instance pattern (Start node + separate Stop node) meant Stop's `stopAll()` closed *its own* (always-null) socket instead of Start's real one — leaking the UDP port (`EADDRINUSE` on next Start). Fix: moved the socket itself onto `robot._egmSocket` too; `bindSocket()` defensively closes any stale reference first. Also fixed: if `EGMJOINT` acks but the local UDP bind then fails, `start()` now sends the graceful-stop signal as best-effort cleanup instead of abandoning the controller-side session.

**Node-only fix (2026-07-10)**: after `stop()`, a stray in-flight UDP frame during the ~1s graceful-stop window could re-trigger baseline-capture logic. Fixed: `onFrame` returns early if `!node.robot || !robot._egmActive || !robot._egmSocket`.

**Prerequisites (one-time, RobotStudio-only)**: a UDP Unicast Device `EGM_PC` (Controller→Configuration→Communication→UDP Unicast Device; Remote Address = Node-RED host's IP, Remote Port = `gofa-egm`'s UDP port (default 6510), Local Port = 0; needs controller restart) + a host firewall rule allowing inbound UDP on that port. **`EGM_PC`'s Remote Address drifts the same way the robot's own IP does** — stale address means `EGMJOINT` acks, UDP binds fine, but zero frames ever arrive and RAPID hangs indefinitely (nothing times out on its own — see the mode-exit history above). Readable over RWS: `GET /rw/cfg/SIO/UDPUC_HOST/instances/EGM_PC` (domain `SIO`, type `UDPUC_HOST`; six domains total: `EIO`,`MMC`,`MOC`,`PROC`,`SIO`,`SYS`). **Not writable over RWS** — `OPTIONS` claims POST is valid but a form-encoded write gets a clean `400` (body-encoding mismatch, not chased further, low value for a one-time setting). RobotStudio remains the way to change it.

**Caution — a config change in the wrong domain can silently miss `EGM_PC` and revert other things.** Live incident: a fix intended for `SIO` landed in `EIO` instead (confirmed via elog) — `EGM_PC` stayed stale AND `ABB_Scalable_IO_0_DO16`'s Access Level reverted `All`→`Default` as a side effect, breaking `gofa-egm`'s RWS stop-signal write (`403`). Always confirm which domain a change actually landed in (the elog says so).

**Fallback added (2026-07-17) after that incident**: `gofa-egm`'s `stop()` (`setStopSignal()`) falls back to the Background-task transport (`socketSend({cmd:'setdo',name,val}, robot.backgroundPort)`) if the direct RWS write 403s — RAPID always has I/O access regardless of RWS Access Level. Without this, an Access-Level regression leaves an active EGM session permanently stuck with no way to trigger graceful stop. Confirmed live end-to-end after the fix.

**Tool load data**: ABB's EGM manual requires correct tool load data (`LoadIdentify`) before EGM — can't be run with nothing mounted (needs a real physical tool to characterize). **Addressed for the current no-tool state (2026-07-21)**: both `.mod` files were found using the placeholder `tGripper` tooldata (`[0,0,100]` offset, 1kg) on **every** motion instruction, not just EGM — a real mismatch, since `gofa-pose`/`gofa-save-point`/`gofa-subscribe-pose` read position via RWS `tool=tool0&wobj=wobj0` (unrelated to RAPID's active tool), so a saved point would replay ~100mm off. Fixed: both files now target RAPID's built-in `tool0` (empty flange, zero mass) for all motion; `tGripper` stays declared/unused as a placeholder. **Upgrade path**: once a real gripper is mounted, run `LoadIdentify`, populate `tGripper`'s real values, switch every motion instruction's tool argument back from `tool0` to `tGripper`.
