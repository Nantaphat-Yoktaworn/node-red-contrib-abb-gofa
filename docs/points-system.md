# Saved points format

**Every point lives on the robot controller's own disk (2.5.0+) — no local/Node-RED-host storage.** JSON file at `gofa-robot`'s Remote Points Path (default `$HOME/Programs/gofa_points.json`), managed purely via RWS `fileservice` GET/PUT (`remoteGetPoints`/`remoteAddPoint`/`remoteDeletePoint`/`remoteFindPoint`/`remoteSavePoints`) — same mechanism `gofa-file` uses:
```json
[{ "id": "uuid", "name": "pick1", "target": { "x":323.2, "y":-81.8, "z":807.0, "q1":0.267, "q2":0.129, "q3":0.954, "q4":-0.053, "cf1":-1, "cf4":-1, "cf6":0, "cfx":0 } }]
```
GOTO token rounds to 1dp (xyz)/4dp (quaternion) to stay under RAPID's 80-char string limit; RAPID re-normalizes the quaternion. Doesn't touch `MainModule.mod`/RAPID — movement doesn't know or care where the point came from.

Originally considered storing the list inside RAPID, but RAPID's `string` type has a hard 80-char cap (see GOTO-token rounding) that a growing point list would blow past. `fileservice` GET/PUT sidesteps that entirely (confirmed live: missing file → clean `404`, treated as `[]`; PUT **requires** `Content-Type: text/plain;v=2.0` or `application/octet-stream;v=2.0` — `application/json` is `415`-rejected). No concurrent-write protection — acceptable for human-paced point-teaching.

**Local storage removed entirely (2.5.0, same day as the `gofa-points` merge, by direct user request).** Removed from `gofa-robot.js`: `pointsFile` config, `_points`/`_pointsMtime`, `_loadPoints`/`_savePoints`/`getPoints`/`addPoint`/`deletePoint`/`findPoint`/`replacePoints`, `atomicWriteFileSync`/`fileMtimeMs`, the `/gofa-robot/:id/points` admin route. `gofa-sequencer` lost the same `storage: 'local'|'remote'` option, always calls `remoteGetPoints()` now. `export`/`import` repurposed (not removed): export reads on-robot list via `remoteGetPoints()` (optional local backup file); import validates (`validatePointsArray()` in `gofa-points.js`) then `remoteSavePoints()` **replaces** the robot's on-disk list.

## Combined points node (`gofa-points`, 2.5.0)

`gofa-save-point`/`gofa-go-point`/`gofa-point-list`/`gofa-delete-point` removed, folded into `gofa-points` as Action-dropdown options (`save`/`go`/`list`/`delete`, alongside existing `export`/`import`), by direct user request. Six `do*` functions (`doSave`/`doGo`/`doList`/`doDelete`/`doExport`/`doImport`) shared by the runtime handler and one consolidated admin route (`POST /gofa-points/:id/run`, replacing five separate routes).

**Payload contract — deliberately NOT the bare-string-is-action convention** used by `gofa-rapid-exec`/`gofa-motor`. Only `msg.payload.action` (object field) selects the action; a bare string means point name (save/go/delete) or file path (export/import), matching the original standalone `gofa-points`' own documented exception. This also fixed a latent inconsistency: the original `gofa-go-point`/`gofa-delete-point` never read a bare string as the name (only `.name`), unlike `gofa-save-point` — now consistent across all three.

**Bug caught mid-build (worth remembering for future merges of this shape)**: the old admin routes had defensive `typeof robot.X !== 'function'` guards the runtime handlers never had. Naively hoisting admin-route logic into the shared `do*` functions carried those guards into the runtime path too — a real behavior change that broke test mocks with intentionally-partial method sets. Fixed by stripping the guards from the shared functions (a missing method now throws inside `.then()`, auto-caught by existing `.catch()` at both call sites) — admin-route friendliness is lost only for the rare not-fully-initialized-config-node case; runtime behavior stayed byte-identical to the five original nodes. Caught by running the test suite, not by inspection.

**No known chaining hazard**: none of the six actions' success payloads include an `action` field; override field names (`path`/`savePath`/`loadPath`) are distinct from output field names (`savedTo`/`loadedFrom`) — chosen specifically to avoid the collision class `gofa-rapid-exec`/`gofa-asi-led` have (see `docs/rapid-protocol-notes.md`). Not separately live-verified by chaining, just by field-name inspection.

**Confirmed live end-to-end (2026-07-31, IP had drifted to `192.168.20.59`)**: full `list`→`save`→`list`→`go`(±30mm Z, 20% speed cap, real physical motion confirmed by human)→`go`-back→`export`→`delete`→`list` cycle against a dedicated scratch file, repeated with `storage:'remote'`. `import` deliberately not live-tested (local-file-only, destructive to real data, already covered by unit tests).

**Found and fixed an unrelated real bug in the process**: first socket PING timed out despite RWS reporting RAPID running — the exact shape the watchdog flow treats as a genuine wedge (see `docs/version-handshake-watchdog.md`). A manual stop/resetpp/start did NOT clear it — pointing away from the wedge bug and toward stale `SERVER_IP` (robot's IP had drifted again while the loaded module still had the old IP baked in). Running `gofa-setup` (which rewrites `SERVER_IP` on every upload) fixed it immediately. **Lesson**: check `SERVER_IP`-vs-actual-IP drift before assuming the unexplained wedge bug — a recovery cycle that does nothing is itself a signal the cause is elsewhere.

**Migration**: `flows/`/`examples/` updated (`"type": "gofa-points"` + matching `"action"` field; existing config fields reused). Same day, local storage removed entirely — every migrated node's now-meaningless `"storage"` field stripped from `flows/`/`examples/` and this maintainer's real local `flows.json` (backed up first). No compatibility shim for external flows — replace, not alias, per user request. Bumped to 2.5.0 (Node-RED/admin-route only, no RAPID/socket protocol change, no `MODULE_VERSION` bump).

**Confirmed live same day (2026-07-31)**: `save`→`export`(no path)→`export`(with backup path)→`import`(from backup, replacing on-robot test list)→`list` round trip against a dedicated on-robot test filename (never the real `gofa_points.json`) — all passed, no motion involved.

The editor panel's single "Run Action Now" button/point-selector proxy dropdown (`#node-select-pointName` mirrors into the real bound field `#node-input-pointName`, needed because the Point Name text field and the Point selector `<select>` can't share one `id`) was **not** separately live-tested — only the six actions' underlying `on('input')` behavior was, via the same code path the editor's admin route also calls.
