# RAPID socket protocol — gotchas and history

Detail doc for the command table in `CLAUDE.md`. Read this when debugging the socket protocol, editing `MainModule.mod`/`MainModuleEGM.mod`, or hitting an unexplained `ERR:*`/timeout.

Ack is sent **before** motion starts. RAPID error handler keeps the server alive on motion faults. **Move commands are blocking (no `\Conc`) as of 2.4.2** — only jog commands still queue via `\Conc`.

**80 characters is a hard ceiling on every request — and the goto JSON exceeded it (fixed 2.6.3).** RAPID's `string` type holds 80 chars, and `ServeClient` reads each line into one (`SocketReceive clientSocket \Str:=rxStr`). Longer lines are **truncated at 80 on the controller before any parsing** — no error, no ERRNO, just a short string that the hand-rolled scanners then reject. goto is the only command that gets near it: 11 numbers, and the JSON framing `{"cmd":"gotoj","val":[…]}` costs 24 chars before a single digit, so real GoFa 12 targets serialize to 81–83 and the worst reachable case is ~91 — the JSON form of goto could *never* fit. Truncation removed the closing `]}`, `GetJsonNumArray` found no `]`, and the reply was `{"status":"err","cmd":"gotoj","msg":"invalid target"}` → `ack: "ERR:GOTOJ"` with no motion. It read as point-specific because the overrun depends on the digit count of that point's coordinates: at 81 chars only the `}` is lost and the request still parses (the `]` survives at position 80), at 82+ the `]` goes and it fails — so of three points taught for the Pick & Place Sorting Flow, one landed on 81 and worked while two landed on 83 and did not. **Fix is palette-side, no `.mod` change**: `encodeForRapid()` in `gofa-robot.js` emits goto as JSON when it fits and downgrades to the legacy text token (`GOTOJ<x;y;z;…>`, framing 5 instead of 24 → 62–72 chars, worst reachable target 72) when it doesn't; `TryGoTo` parses it into the same `robtarget` and acks the same `OK:GOTO`. **When adding any new command, budget its JSON against 80 chars** — this is the one limit with no runtime symptom pointing at it. Only goto has a text fallback; anything else that overruns needs a shorter encoding or a multi-message design.

**GETVAR/SETVAR**: names uppercased by `CleanCmd`; string values preserved from `rawclean`. New PERS var needs an `ELSEIF` in both `TryGetVar`/`TrySetVar`. Built-in: `nTestVar` (num), `sTestMsg` (string).

**Case-sensitivity gotcha — not universal.** Legacy text protocol is fully case-insensitive (`CleanCmd` upper-cases the whole line). `DispatchJson` gets raw JSON with no blanket uppercasing (would corrupt string-valued fields) — each handler normalizes case itself, if at all. `getvar`/`setvar` DO normalize (`StrMap` upper-cases `name`). `setdo` originally did NOT — `gofa-do-write.js` now upper-cases the signal name before sending over Socket. Check the specific `CASE` block before assuming case-insensitivity.

**SETLED/RESETLED**: `SetGO` on `Asi1LedRed/Green/Blue/Period` via `TrySetLed`. Software counted blink handled by `gofa-asi-led` (period ignored/0 when blinking). Three transports: Socket (`MainModule.mod`, original), RWS (`/set-value` — dead end on this hardware, ASI board has no editable Access Level), Background task (`BackgroundLed.mod`, the one actually used in the teach workflow — see `docs/background-led-task.md`).

**RWS I/O write — use `/set-value`, not `/set`.** `POST /rw/iosystem/signals/{name}/set` is wrong (`404` on OPTIONS, `405` on POST for every signal). Correct: **`POST /rw/iosystem/signals/{name}/set-value`** (body `lvalue=<value>`) — `204` on `Access: All`, `403` (correctly) on `Access: Default`. `gofa-do-write.js`/`gofa-ao-write.js` fixed to use this. Access level must still be `All` (RobotStudio → Controller → Configuration → I/O System → Signal → Access Level, needs restart).

**SETDO (socket alternative)**: `TrySetDo` uses RAPID `SetDO` against an allow-list (`ABB_Scalable_IO_0_DO1`..`DO16`). `ERR:UNKNOWN_SIGNAL`/`ERR:PARSE` on bad input. Works regardless of RWS Access level (RAPID always has `Rapid` access) — useful when you don't want to open Access to `All`.

**`gofa-do-write` Transport dropdown**: **RWS** (default, `/set-value`, needs `Access: All`) or **Socket** (`{cmd:'setdo',name,val}` → `DispatchJson`'s `"setdo"` case, NOT legacy `TrySetDo` — case-sensitive, no `CleanCmd` uppercasing). `gofa-do-write.js` upper-cases the name before sending over Socket.

**Analog nodes removed (2026-07-07)**: `gofa-ai-read`/`gofa-ao-write` deleted — this controller has zero AI/AO signals (DSQC1030 is digital-only, C30 has no native analog port). Would need ABB's DSQC1032 Analog Add-On module. Re-add if installed (same `/set-value`/plain-GET pattern).

**`gofa-backup`/`gofa-restart` removed (2026-07-14)**: ABB's documented `POST /ctrl/backup?action=backup` and `POST /ctrl` (restart) both `405` live despite `Allow` headers claiming POST is valid, on this controller (RobotWare 7.21.0+229). No working alternate path found; re-add only if a working trigger call is confirmed live first.

**SERVER_IP**: `MainModule.mod`'s `CONST string SERVER_IP` must match the controller's real IP or `SocketBind` silently fails (every socket command times out, no error). `gofa-file` upload / `gofa-setup` / `gofa-mod-edit` auto-rewrite it (`patchServerIp`, no-ops on files without the constant) to the `gofa-robot` config node's IP on every upload.

**`loadmod`/`unloadmod`/`activate`**: documented `POST /rw/rapid/tasks/{task}?action=loadmod` is `405` (Allow header lies). Working call: **path-based** `POST /rw/rapid/tasks/{task}/loadmod`, body `modulepath=<path>&replace=true`, requires `Accept: application/hal+json;v=2.0` (the one exception to xhtml Accept in this whole palette). Gated on edit mastership. `replace=true` only replaces a *same-named* module — loading a different-named module while the old one is loaded leaves both, both declaring `PROC main()`, and `resetpp`/`start` fail with `(87,5): Global routine name main ambiguous`. Fix: `unloadmod` (`POST .../unloadmod`, body `module=<name>`, same hal+json/mastership reqs) first — only detaches from the task, file stays on disk. `activate` (`POST .../activate`, body `module=<name>`) works the same way. **All three require RAPID stopped** (`204` when stopped, `403` when running). `gofa-rapid-exec` surfaces the RWS error's reason text and hints for this rejection.

**RAPID start note**: `POST /rw/rapid/execution/start` returns HTTP 200 even on silent rejection (e.g. error 20055 "must start in Motor On state"). `gofa-rapid-exec`'s `start` action reads `/rw/panel/ctrl-state` first (fails fast if motors off), then polls `ctrlexecstate` up to 1.5s to confirm `running`. `stop`/`resetpp` don't have this failure mode.

**RAPID symbol data — confirmed impossible on this controller.** `/rw/rapid/symbol/data/...` is `404` (this controller advertises `symbols`, plural, a search-based resource — RWS 1.0 vs 2.0 shape split, same as `execution`/`iosystem`). ABB's own documented `POST /rw/rapid/symbols?action=search-symbols` also `405`s despite its own `Allow` header. Not a licensing issue (verified RWS is base-included, RobotStudio Connect [3119-1] is unrelated/WAN-only). This is why variable read/write goes through the custom `GETVAR`/`SETVAR` allow-list protocol. `gofa-subscribe-var` goes straight to module-text (no dead-endpoint round trip).

**IO subscription**: WS subscribe resource suffix must be **`;state`**, not `;lvalue` (which always got `400`). Fixed in `gofa-subscribe-io` — confirmed live with real WS push (not polling) down to a single button tap.

**Change-only, no initial snapshot**: WS subscriptions only push on a *transition*, never emit current value on connect. A fresh subscribe can sit silent for seconds with nothing touched — expected. A second `on('input')` while already subscribed triggers `readOnce()` (a genuine one-off GET) for current value.

**Elog subscription**: subscribable resource is the **bare** `/rw/elog/<domain>` path, no `;suffix` (unlike every other subscribe node). WS push carries only a reference (`seqnum`+`href`); node does a follow-up `GET ...?lang=en` using XHTML class `elog-message` (singular, differs from the bulk-list `elog-message-li` class `gofa-elog` parses) — `gofa-subscribe-elog.js`'s `parseEntry()` matches either.

**Elog domain vs. severity**: domain is a fixed ABB category list (`0`=Common,`1`=Operational,`2`=System,`3`=Hardware,`4`=Program,`5`=Motion,`7`=IO&Comm,`8`=User,`9`=Safety,`10`=Internal,`11`=Process,`12`=Configuration,`13`=Paint,`15`=RAPID,`17`=ConnectedServices) — NOT severity, and domain `0` is not "all domains" (it undercounts vs. e.g. domain `10`). Severity (`msgtype`: 1=info/2=warning/3=error) is separate. Both `gofa-elog`/`gofa-subscribe-elog` have a client-side **Min Severity** filter plus the corrected domain dropdown.

**ASI buttons**: physical buttons are plain `DI` signals `Asi1Button1`/`Asi1Button2` — readable via `gofa-di-read`, subscribable via `gofa-subscribe-io`. Works even when FlexPendant Wizard has a button bound to a function (Wizard reads the same signal, doesn't claim it exclusively). Enables a "teach" workflow: hand-guide, tap button, `gofa-subscribe-io` → `gofa-save-point`.

**Module-text fallback (`gofa-rapid-var-read`/`gofa-subscribe-var`) is confirmed STALE**, not live — reflects the module's compiled/declared value, not runtime value (proven: wrote via socket `SETVAR`, confirmed via socket `GETVAR`, but RWS module-text still showed the original value). Both nodes mark it `stale: true` with a `warning` field. No live-value alternative outside the `TryGetVar`/`TrySetVar` allow-list exists.

**`gofa-rapid-exec` chaining hazard**: its success output `{ok:true, action:<ran>}` matches the shape its own `msg.payload.action` override reads. Chaining two instances (even through a passthrough `switch`) makes the second silently repeat the first's action. Fix: a `change` node resetting `msg.payload` to `{}` in between. Bit `flows/teach_flow.json` live (`resetpp`→`start` chain silently repeated `resetpp`).

**`gofa-asi-led` has the same hazard**, different trigger: its output `{ok,r,g,b,blinks,transport}` gets read by `resolvePayload()`'s color-override logic in a chained second instance. Bit `flows/teach_flow.json` live (white flash bled into a yellow-configured node). Same fix (clearing `change` node in between). **General rule**: any node whose success payload reuses field names that node's own type accepts as an override is chaining-unsafe.

**Joint soft-limit (2.4.9)**: `gofa-movej` validates absolute-joint targets against per-axis limits before sending → clean `{ok:false,error,joint,value,min,max}` instead of a RAPID motion fault. Defaults = true CRB 15000-12/1.27 hardware range (`JOINT_LIMITS` in `gofa-robot.js`: J1 ±270, J2 ±180, J3 −225/+85, J4 ±180, J5 ±180, J6 ±270, per manual 3HAC077389-001) — only rejects targets that would fault anyway. Optional JSON override on `gofa-robot` config (six `[min,max]` pairs). **Does NOT apply to Cartesian moves** (`gofa-go-point`/`GOTOJ`) — no node-side IK available; relies on RAPID's own fault handling. Node-side only; RAPID does no check itself.

**`SPEED`/`SpeedRefresh` vs `VelSet` — RESOLVED, use `VelSet`.** `gofa-speed-set` originally used `SpeedRefresh`, which live-testing proved is a SEPARATE override from the FlexPendant/`speedratio` dial (confirmed: setting `SpeedRefresh 40` didn't change RWS `speedratio`) and, worse, has **no measurable effect on real motion when called from an idle socket handler** (ABB's own semantics: it only updates an *already in-progress* move). **Fix (2.4.6)**: `MainModule.mod`/`MainModuleEGM.mod`'s `"speed"` case now calls `VelSet speedVal, 5000;` (the `5000` mm/s cap is generously above anything this project ever commands, so only the override% binds) — `VelSet` changes the *programmed* velocity persistently. Live-verified: 30° joint-6 move took ~37ms at 100% vs ~2216ms at 5% (60x, unambiguous). New `"getspeed"` case reads `C_MOTSET.vel.oride` (note the underscore — `CMotSet` without it fails to compile) → `VAL:<n>`, mirrored by `gofa-speed-set`'s Read action. **Legacy plain-text `SPEEDnn`/`TrySpeed` handler had the identical stale-`SpeedRefresh` bug in a separate code path** (2.4.7) — never hit by Node-RED (which always sends the JSON form) but shipped/documented in `MANUAL_CONTROL.md`, so fixed too; also added legacy `GETSPEED`. Both `.mod` files carry the fix.

**`\Conc` queue-depth crash — FIXED 2.4.2, real production bug.** Chained motion used `\Conc` (async ack) plus a `WaitRob \InPos` sync helper meant to avoid RAPID error 40631 ("too many move instructions in sequence"). **Five independent live-tested sync strategies all failed at the identical move** — proved `WaitRob \InPos` wasn't resetting whatever RAPID tracks for this limit; not a tuning problem. **Fix**: removed `\Conc` entirely from all move procs/handlers in both `.mod` files — ack already precedes the move, so RAPID just finishes each move before serving the next command. Confirmed 20/20 clean cycles after (vs. 100% failure by move 7 before). Jog commands untouched (each does its own `StopMove`/`ClearPath`/`StartMove` before a single `\Conc` move — never exposed to this bug). **Trade-off**: `STOP` can no longer interrupt an in-progress blocking move, only a not-yet-started one. Hardware e-stop is independent either way.

**Mid-move STOP (2.4.12)**: `gofa-stop-motion` gained a **mode** dropdown. **`immediate`** (default, node-only, no RAPID change): RWS `POST /rw/rapid/execution/stop` (halts instantly, independent of T_ROB1's blocked socket loop) → `resetpp` (BEFORE `start`, so it restarts from top of `main()` not mid-move — `main()`'s `LoadHome` does no motion, arm stays put) → `start` → poll `ping` up to 8s to confirm socket recovery. Needs Auto + motors on. Live-confirmed: slow move halted ~111° short of target, arm stayed, socket recovered. **`queued`** = legacy socket `STOP` (only cancels a not-yet-started move). **Rejected approach**: a RAPID `ISignalDO`→TRAP interrupt — halts correctly but the aborted blocking `MoveAbsJ` never returns, so the serve loop hangs anyway and needs `resetpp`+`start` regardless; bought nothing over the RWS-stop path. Do not re-add without a fundamentally different mechanism (e.g. two-task split) — see `ideas/issue-3-midmove-stop-plan.md` Phase D. **Not a safety function** — the physical e-stop remains the only real safety layer.
