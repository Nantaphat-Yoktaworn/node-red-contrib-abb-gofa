# Background LED task (`BackgroundLed.mod`, added 2026-07-17)

**Problem solved**: the teach workflow stops all of `T_ROB1` (including its socket server) before lead-through — killing `gofa-asi-led`'s Socket transport for the whole session. RWS transport doesn't help either — this controller's ASI board has no editable Access Level at all (confirmed live; unlike a regular I/O add-on).

**Fix**: `rapid/BackgroundLed.mod` — a standalone RAPID module (own copies of JSON helpers, since RAPID modules in different tasks can't call each other's local PROCs) serving `ping`/`setled`/`resetled`/`setdo` over its own TCP port (`LED_SERVER_PORT := 1026`, matches `gofa-robot`'s `backgroundPort`). Runs in a **separate RAPID task**, not `T_ROB1`, relying on licensed RobotWare Multitasking `[3114-1]` (confirmed via `GET /rw/system`).

**Generalized to a background-services task**: beyond LED, fixes anything depending on `T_ROB1`'s socket that breaks when it's stopped — `setdo` added to `BackgroundLed.mod` (same allow-list as `TrySetDo`, since digital I/O is task-independent); `gofa-do-write` gained a **Background task** transport; `gofa-connection-status` pings `backgroundPort` as a third independent check (`msg.payload.background`), distinguishing "T_ROB1 stopped" from "controller unreachable"; `gofa-egm` sets the LED magenta via Background transport while streaming (best-effort, never blocks EGM). **Out of scope**: PERS-variable read/write via the background task — whether a `T_ROB1`-declared PERS var is visible to `T_LED` code is unconfirmed and untested.

**Reload procedure (confirmed live, needed only for the very first load — see "Remote reload" below for updates)**: `T_LED` is `SEMISTATIC`, NOT stopped by `POST /rw/rapid/execution/stop`. Real working procedure: (1) Controller in Manual mode. (2) FlexPendant → Execution menu → check "Handle static and semi-static tasks the same way as normal task regarding start/stop" (the only way found to make `T_LED` stoppable at all — no RWS/RobotStudio path). (3) Press Stop → stops `T_ROB1` and `T_LED` together. (4) **RWS `loadmod` is blocked here** — FlexPendant holds edit mastership locally (`403`), and RWS mastership needs Auto mode which undoes the stop. **Load directly on the FlexPendant**: upload the file first via `gofa-file`/RWS (only file transfer, not load), then ABB menu → Program Editor → switch task to `T_LED` → File → Load Module → confirm Replace. (5) Verify via `GET /rw/rapid/tasks/T_LED/modules/BackgroundLed/text` → follow the `file-path` reference. (6) Restart both tasks, then **uncheck the Execution-menu setting again** — leaving it on means every future ordinary stop also stops `T_LED`, defeating the point.

**Confirmed live (2026-07-17): RWS cannot create a new task, only RobotStudio can.** `GET /rw/cfg/sys/CAB_TASKS/instances/T_ROB1` exposes the schema and `Allow` looked promising (same shape as the `loadmod` red herring), but four different `POST` variants against `.../instances` all `405`d with zero side effects — a genuine structural limitation (task creation needs boot-time registration), not a wrong-URL case. Don't re-attempt without a new concrete reason (RobotWare update / new official docs).

**Confirmed live: the core premise (`T_ROB1` stop doesn't touch other tasks) holds.** Stopping `T_ROB1` left this controller's own pre-existing `SC_CBC`/`T_GOFA_LED` (both `semistatic`) at `excstate: started` throughout.

**This controller already has a task `T_GOFA_LED`** running `GOFA_Main` — almost certainly ABB's own built-in collaborative-status-light driver (explains the locked ASI Access Level). **Confirmed off-limits**: reading its module text returns `500 "Module encoded, noview or readonly"`. **Do not attempt to read/edit/repurpose it** — `BackgroundLed.mod` must run in its own separate task.

**One-time RobotStudio setup (RWS cannot do this)**: (1) upload `BackgroundLed.mod` (already done, standard `SERVER_IP`-patched upload). (2) Controller→Configuration→Controller→Task → add task `T_LED`. (3) Type `SEMISTATIC` (auto-starts, resets PP each restart, independent of Program Start/Stop — confirmed empirically). (4) **Set `TrustLevel` to the least-severe option, NOT the field's default (`SysFail`)** — confirmed a new task instance defaults to the same `TrustLevel` as `T_ROB1`'s real motion task, meaning an unhandled error in this cosmetic task would be treated as a full system failure by default. `T_GOFA_LED` itself runs at `trust="None"` (its own config is read-only/hidden, so the exact dropdown label mapping couldn't be directly confirmed — pick whichever RobotStudio option is least severe, commonly `NoSafety`). (5) Assign `BackgroundLed.mod` to `T_LED`, not `T_ROB1`. (6) Restart controller.

**CONFIRMED LIVE END-TO-END, including physical visual verification**: `ping`/`setled`/`resetled` all worked over port 1026 while `T_ROB1` was genuinely stopped; physical LED color change independently confirmed by a human watching the robot (steady, not flicker); full stop→LED cycle→restart ran clean with both tasks healthy. Also confirmed against the real deployed `teach_flow.json` with physical ASI button presses.

**Safety controller drives the physical LED and overrides custom colors — by design, not a bug.** Confirmed sequence: **white** (~3s during lead-through negotiation) → **yellow** (only while actually moving, instantly overrides/reverts, confirmed the underlying signal values held steady throughout — override is hardware-level) → our own idle color, visible only when genuinely stationary and neither of the above is asserting.

**Most of that "white ~3s" was a real bug, fixed 2026-07-20** — `gofa-leadthrough.js`'s `enable` unconditionally sent a socket `{cmd:'stop'}` to clear queued moves, which is guaranteed to fail (5s timeout) once RAPID's already stopped (the normal case, since the teach flow stops RAPID first). Instrumented: 6324ms total, 5003ms pure wasted timeout. **Fix**: `clearQueuedMovesIfRunning(robot)` checks `ctrlexecstate` first (~10ms) and skips the socket call when already stopped (falls back to attempting it if the check itself fails, preserving the safety property). Confirmed: `enable` with RAPID stopped now resolves in 44ms. The genuine ~3s white period during a real RAPID-running→enable transition is unaffected and expected (real safety-controller negotiation).

**Idle color changed cyan→yellow, point-saved flash changed white→yellow (2026-07-20, by request)** — deliberate: since yellow-while-moving always wins anyway, using yellow as idle/flash color too means no visible color churn between idle/saved/moving during a session. "LED: Teach Mode OFF" still resets to green.

**Node-RED side**: `gofa-robot`'s `socketSend(cmd, port)` takes an optional port override. `gofa-asi-led`/`gofa-do-write` both gained a `'background'` Transport option using this.

**Remote reload (2.4.13, added 2026-07-24) — manual FlexPendant procedure now needed only for the very first load.** `BackgroundLed.mod` gained the same `ISignalDO`→`TRAP` self-stop pattern as EGM's graceful stop: `TRAP TrapLedStop` (body `Stop;`) connected via a new dedicated signal **`ABB_Scalable_IO_0_DO15`** (deliberately NOT `DO16`, EGM's own signal — sharing would make an EGM stop also kill `T_LED`, since digital I/O is task-independent). A `ledStopConnected` bool guards `CONNECT` (re-connecting an already-connected `intnum` is fatal RAPID error 40166 — caught by review before shipping).

**Three genuinely new mechanics, not in ABB's docs, found live**: (1) `T_LED`'s `loadmod` requires the GLOBAL `/rw/rapid/execution` state stopped, not just `T_LED`'s own per-task `excstate` — so `gofa-setup`'s `T_LED` reload sub-chain must run BEFORE `T_ROB1`'s motors-on/start steps. (2) `resetpp` alone does NOT move `T_LED` from `stopped` to `ready` — `loadmod` does (kept `resetpp` anyway, defensive/near-zero cost, per a review finding that `Stop`-from-TRAP resumes *inside the TRAP* on a bare continue). (3) Bringing a `ready` `T_LED` to `started` sometimes needs a **second, identical** `execution/start` call — confirmed live twice; `alltaskbytsp=true` made no difference, plain `alltaskbytsp=false` (same body `T_ROB1` uses) is what works, just sometimes twice. Undocumented by ABB (confirmed via forum search) — purely empirical on RobotWare 7.21.0+229.

**`gofa-setup` now reloads both `T_ROB1` and `T_LED` in one call** (`prepareLed()`/`finishLed()` in `nodes/gofa-setup.js`, shared runtime/admin logic). Step order: preflight → stop RAPID → unload conflicting module → upload/load `MainModule.mod` → resetpp → **stop T_LED → upload/load `BackgroundLed.mod` → reset T_LED PP** → motors on → start RAPID → socket PING → **confirm T_LED started → ping T_LED**. **Best-effort**: any T_LED-side failure is recorded but never fails the overall run; missing T_LED skips the sub-chain cleanly. **One-time prerequisites (not automatable)**: the manual FlexPendant load of this TRAP-enabled version once (bootstrap only), and `ABB_Scalable_IO_0_DO15`'s Access Level set to `All`.

**Confirmed live end-to-end (2026-07-24)**: all 15 `gofa-setup` steps `ok:true` in one call (both runtime and admin-endpoint paths), `T_LED` needing the predicted second `start` kick both times, `gofa-connection-status` afterward showing both module versions `match` at 2.4.13.
